## 1. この文書の目的

画面より先にデータの形を決めるための文書。
特に「あとから足すのが難しい構造」を先に押さえておく。

## 2. v1 で確定させたもの

| テーブル | 役割 | 状態 |
|----------|------|------|
| `works` | 作品 | 確定 |
| `episodes` | 話 | 確定 |

型定義は `src/types/work.ts` / `src/types/episode.ts`。
カラム名は snake_case で、Supabase のカラム名とそのまま一致させている。
変換レイヤーを作らずに済ませるため。

### 決めたこと

**話の順番は `ep_number`（整数の連番）で持つ**

小数（1.5 のような間の値）を使う設計もあるが、
「第◯話」という表示に整数がそのまま使えるほうが扱いやすい。
並び替えのたびに 1 から振り直す。話数が数千になれば見直す。

**`char_count` を保存する**

本文から毎回数えると、一覧を出すだけで全話の本文が必要になる。
保存時に確定させ、一覧は本文を読まずに描ける。

**話のステータスに「公開済み」を入れない**

`todo` / `writing` / `done` は執筆の進み具合であって、
読者に見えているかどうかとは別の話。
公開状態は v2 の公開設定側に別カラムとして持たせる。
ここを混ぜると、「書き上げたが公開はまだ」が表せなくなる。

## 3. 資料（作品世界）

### 3-1. なぜ「ページ」と「項目」の2段構えなのか

資料の種類を型で表すと、種類を増やすたびにコードを書くことになる。
作者が自分で「証拠品」「部活動」「怪異」を作れるようにするため、
**入力欄の構成そのものをデータとして持つ**。

```
resource_pages
  id, work_id, builtin_key, label, description,
  kind ('entries'|'timeline'|'relations'|'plot'|'notes'),
  fields (jsonb),  -- [{ key, label, type, options }]
  is_pinned, sort_order, timeline_mode

resource_entries
  id, work_id, page_id, name, summary,
  values (jsonb),  -- fields に対応する値
  is_major, is_candidate, candidate_source
```

`kind` が5種類あるのは、並べ方そのものが違うものだけを分けたため。
大半のページは `entries`（一覧＋詳細）で足りる。

### 3-2. 常設ページと任意ページ

常設は**どのジャンルでも要るものだけ**。
恋愛作品に組織欄を、日常作品に年表を押しつけない。

| 常設 | 任意（作者が足す） |
|------|--------------------|
| 人物 / 場所 / 関係図 / 出来事・時系列 / プロット・構成 / メモ | 組織・グループ / 用語・設定 / アイテム・小道具 / 事件・謎 / 図・マップ / 自作ページ |

名称の変更にも理由がある。

- 「地名・場所」→**「場所」**。教室も喫茶店も事件現場も同じ場所として扱うため
- 「組織・国家」→**「組織・グループ」**。部活も家族も入るようにし、国家は種類の一つに下げた
- 「年表」→**「出来事・時系列」**。年表は歴史ものの言葉で、日常作品の一週間には使えない

### 3-3. 出来事の時間

`timeline_mode` で表し方を切り替える。
年月日 / 作中の日数 / 主人公の年齢 / 第何話 / 時刻 / 順番だけ。

作中の暦は現実の日付型に収まらないので、値は文字列で持つ。

### 3-4. 関係

```
resource_relations
  id, work_id, from_entry_id, to_entry_id, label, note,
  changes (jsonb)  -- [{ at, label }]
```

人物同士に限らない。人物と組織、人物と場所、人物と事件も同じ形で結べる。

**関係を1つのラベルで固定しない**のが要点。
「初対面 → 警戒 → 信頼 → 決別」を1語で表すことはできないので、
話数に沿った変化を配列で持つ。

### 3-5. プロット・構成

```
plot_stages
  id, work_id, title, description, episode_range, sort_order
```

「導入・旅立ち・試練・真相・転機・終幕」のような決まった段は持たせない。
あれはファンタジーの型であって、物語一般の型ではない。

**このページでは AI補助を使わない。** 骨格を決めるのは作者の仕事だから。

### 3-6. 本文からのリンク

```
entry_mentions
  id, work_id, episode_id, entry_id, surface
```

本文に記法（HTMLタグや独自マークアップ）を埋め込む方式は採らない。
本文を素のテキストのまま保てば、
縦書き表示・TXT/PDF書き出し・将来の投稿サイトへの転送が記法に縛られない。

### 3-7. AI補助

資料は**本文から埋まる**のが基本。作者がすることは承認・訂正・拒否の三択で、
名前を打ち込む作業は原則発生しない。手で書くのはプロットとメモだけ。

```
ai_settings
  work_id, is_enabled, auto_extract,
  approval_mode ('manual'|'draft'),
  extract_characters / places / organizations / terms / events,
  suggest_links, generate_images
```

`candidate_status` は 3 値。

| 値 | 意味 |
|----|------|
| `none` | 承認済み。資料の本体 |
| `pending` | 候補。一覧には混ぜず、上部の候補欄に出す |
| `rejected` | 拒否済み。次に拾ったときも候補にしない |

**rejected を覚えるのが要点。** 覚えないと、本文を保存するたびに
同じものが並び続けて、候補欄が使い物にならなくなる。

経路は二段構え。

```
サーバーに鍵あり → /api/ai/extract → モデル
鍵なし           → 端末内の簡易版（本文は外へ出ない）
```

呼び出し側はどちらでも同じ。失敗したら簡易版へ落ちる。

**できないこと（設定項目としても置かない）**

- 本文の生成
- あらすじ・台詞の生成
- 表紙・挿絵の生成
- プロット・構成への関与

指示文そのものが存在しない（`src/lib/ai/prompts.ts`）。
画面に入口が無いだけでなく、頼む文が無い。

**資料の図案は作る。** 紋章・肖像・風景・記号の 4 種類だけ。
物語そのものではなく、書き手が世界を見渡すための目印だから。
`/api/ai/image` は viewBox・スタイル・外部参照を検査してから返す。

### 3-8. 表記ゆれ

```
resource_entries.aliases  text[]
```

「リオ」「リオ・アルセイン」「リオくん」が別項目として増え続けると、
どれが本物か分からなくなる。これが資料の壊れる一番の原因。

判定は `src/lib/resource/name-match.ts`。
カタカナ→ひらがな、全角→半角、中黒・長音・空白を落として比べ、
包含関係を先に見てから編集距離で測る。

**機械が勝手に統合はしない。** 「同じでは」と並べるところまで。
別人の「田中」を勝手にまとめられたら取り返しがつかない。
同じページの中だけで突き合わせるのも同じ理由（人物の「アルセイン」と
場所の「アルセイン」は別物）。

統合すると、消えるほうの名前は `aliases` へ移り、
関係と本文リンクの向き先も付け替わる。
別名は候補抽出でも「登録済み」として扱うので、同じものが再び候補に出ない。

### 3-9. バージョン履歴

```
episode_versions
  id, episode_id, work_id, body, char_count, trigger, label
```

差分ではなく全文を控える。復元が単純になり、履歴が壊れても他の版に影響しない。

### 3-10. 各種設定

```
work_display_settings   -- 表示設定
work_publish_settings   -- 公開設定
```

**works に status 列は持たない。**
「非公開 / 執筆中 / 公開準備中 / 公開中」は、
公開範囲（下書き・限定・公開）と連載状態（連載中・完結・休載）の
組み合わせで全部表せる。同じことを2か所で持つと必ず食い違う。

## 4. 保存先の切り替え方

現在の保存先は **localStorage**。切り替えの手順は次のとおり。

1. `src/lib/repository/supabase-repository.ts` を作り、`Repository` を実装する
2. `src/lib/repository/index.ts` の `getRepository()` の返り値を差し替える
3. `supabase/migrations/001_initial_schema.sql` を Supabase で実行する

画面・フックのコードは変更しない。
**そのために、localStorage を画面側から直接触らないこと。**
このルールが破られた瞬間、移行コストが跳ね上がる。

## 5. バックアップ

`src/lib/backup/format.ts` に形式を置いている。

```
{ meta: { app, format_version, exported_at, counts },
  tables: { works: [...], episodes: [...], ... } }
```

**保存の実装に依存しない形にするのが要点。**
localStorage の生のキーをそのまま吐くと、
Supabase へ移った瞬間に古いバックアップが読めなくなる。

戻し方は 2 通り。`merge` は id が同じものを飛ばす。
上書きにすると、戻したつもりが今の原稿を潰すことになる。
